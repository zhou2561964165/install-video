# 独立主题规划与逐主题写作：方案 B 设计

> 后续用户要求将A/B结合；当前执行入口为[组合设计](2026-10-15-planned-direct-summary-design.md)。本文保留纯B备选，未实施，其14点/逐主题预算不是组合候选的限制。

日期：2026-10-15。状态：**设计已完成，等待用户审阅；未实现、未测试、未分配真实模型阶段。** 本文落实既有[候选计划](../plans/2026-10-15-topic-writing-candidate.md)的预算和路由取舍；当前依据是[phase13 独立内容审阅](../../acceptance-reports/2026-10-13-long-summary-fidelity/phase-13-content-diagnosis.md)。

工程约定：适用 Superpowers/skills、成熟组件优先、配置化窄接口及单向依赖；yt-dlp 仅经唯一服务，视觉只读 scene，UI 须 ui-ux-pro-max/design-system 与三层 token。保护已有工作、账号/env、本机模型和旧验收字节。本文不授权修改旧 phase，不改变公开入口或生产默认。

## 1. 目标与依据

用户希望字幕经模型形成完整、忠实、可读的概览与详细主题。先执行的 A 已把完整字幕一次交给 Pro。phase13 六项 core 全 full，但仍有时间矛盾、具体实例扩大为类别、两项课程路线遗漏及一处通用重复。按用户既定条件进入 B 设计，保留 A 与原件；不能据一条样本声称 A 架构不可用。

B 的待验证假设是：程序落实主题的来源责任和输出资源，逐主题完成正文，可以减少自由全局生成中的主题遗漏，并避免最后一次 merge 再删选已经写好的内容。它不能机械证明主语范围、时间或条件正确；这些仍由独立内容审阅判断。

本次是新增固定执行边界的架构设计。先由用户审阅本文，随后制定可执行实现计划并选择执行方式；本阶段新增模型 POST 上限为 0。

## 2. 采用现有成熟组件

复用[已有官方资料研究](../../reference-summary-review-2026-10-10.md)及实际安装的 langchain-core 1.6.9、Pydantic v2；继续使用 RunnableSequence/RunnableLambda 和禁追踪上下文，不增加 SDK、自动 Agent 或第三方遥测。

| 选择 | 采用方式与取舍 |
| --- | --- |
| 现有 LCEL/Pydantic | LCEL 执行规划→预检→串行写作→概览；Pydantic 构造和解析动态结构；HTTP 仍由 llm_service 提供 callable。现有生产已采用此依赖，增量最小。 |
| LlamaIndex synthesizer | tree/refine 的递归压缩/更新答案不直接落实本次逐主题责任，首轮不新增依赖。 |
| LangGraph | 适于持久状态、恢复及分支；当前首错终止、没有恢复和反馈循环，现有 LCEL 足够。需要这些能力时另评估。 |

不重做通用摘要引擎。新增代码只负责项目特有的块定位、资源分配与接口适配；使用 Python 标准库保留换行和偏移，不引入语义分句引擎。依赖许可证、安装版本和兼容性沿既有 lock；实现前核对本地依赖清单，新增依赖须重新选型。

## 3. 首轮仅增加内部显式候选

新增内部 `summarize_topics(...) -> LLMSummaryResult`，由独立验收 runner 显式调用，不在此次实现中把第三个模式接入公开请求或默认选择器。入口接收不可变候选配置及窄请求 callable，便于冻结与离线 transport。

- `summary_topics.py`：严格规划类型、原文块/offset、路由和预算计算；无 HTTP、env 或语义评分。
- `summary_pipeline.py`：新增固定 LCEL callable 边界；没有重试边、并行付费调用或部分结果返回。
- `llm_service.py`：候选消息、原生 schema、现有 `_complete`/Responses 解析/输出规范化与结果适配。
- 复用 `summary_output.stage_model/stage_schema` 的主题 points、overview 类型；规划使用内部路由类型，不复用 facts、assessment 或 subject_checks 协议。

不直接调用 `_staged_final`：它会重新生成一遍全局 points。可以复用其 overview 的窄角色适配。复用 `_StagedRunner.perform` 时必须显式关闭其格式修复额度；若无法隔离其诊断/预算职责，则只复用更窄的 `_complete` 与解析函数，不复制整个 runner。

生产默认仍由现有配置决定；内部候选配置不读写本机 env、不提高公开 20,000 字符限制，不宣称产品长文已恢复。

## 4. 来源定位与规划结构

规范化使用已有 `_summary_input`，冻结规范化全文及 hash。来源正文上限 60,000 字符，空输入在任何 POST 前拒绝。

以标准库 `splitlines(keepends=True)` 和连续 offset 建立块；优先在 2,000 字符窗口后半段的换行处结束，没有换行时按窗口边界切分。每块为 `[start,end)`，完整保留字符，最多 60 块。必须验证首块从 0 开始、各块相接、末块到全文末尾、逐块拼接严格等于规范化全文；不能把旧 `_summary_chunks` 的 `strip/lstrip` 结果当作精确 offset。硬边界不代表语义句末。

唯一规划调用读取完整原文块，仅返回：

- `topics`：1–6 个主题；每项含非空标题、点数上限 `point_cap`、至多 2 个额外上下文块 ID。
- `owners`：长度严格等于块数的数组，元素为主题序号，确定每块唯一正文责任主题。

主题标题最多 120 字符，仅作导航。块 ID/主题序号必须有效且严格为整数，不接受 bool、字符串强转、重复字段或额外字段。每主题至少有一块，主题按其第一个责任块的原文顺序排列；非法规划直接失败，不静默重排或重规划。点数上限之和不得超过全局预算。标题和路由不是新事实或语义证据。

## 5. 上下文、跨主题依赖与重复输入成本

主题 writer 收到自身所有责任块、这些块的完整相邻前后块，以及规划显式指定的至多 2 个额外上下文块。同一请求按 offset 去重和排序，非连续区间标明中间存在间隔；角色标签区别正文责任与辅助上下文。

writer 必须覆盖责任块内的重要内容，不能因标题未提到某内容就忽略它。相邻/额外块用于恢复主体、条件和指代；其中独立主题由其责任 writer 处理。writer 只能依据原文，不能依据前一个 writer 的回答作为新事实来源，因此所有写作输入都能在首次写作前确定。

约束：任一原文块最多进入 4 个写作请求，全部 writer 的原文字符投递总和不超过 `4 × source_chars`；超限拒绝整份规划，不删除上下文凑容量。加上规划与概览各读一次完整原文，原文总投递不超过 `6 × source_chars`，提示/schema 另按完整请求封套计数。

相邻块只能改善局部衔接，不能保证跨更远距离的指代已被找全；额外 ID 也只是模型选择。若独立评分发现跨块条件仍丢失，应判内容失败。

## 6. 有限输出与输入封套

保留原 B 候选的全局**至多 14 个主题要点**与写作加概览至多 8,192 output tokens，均是资源上限，不强制凑满。每点可包含完整机制、条件与例子，不设置固定字数或单点 240 字拒绝线，不切字、删点或本地润色。

| 阶段 | 上限 |
| --- | --- |
| 规划 | 1 次，2,048 output tokens |
| 全部主题写作 | T 次，合计 7,168 output tokens |
| 概览 | 1 次，1,024 output tokens |
| 正常及最坏调用 | T+2，T≤6，总计≤8 POST；format/semantic/extra 均 0 |
| 输出总上限 | 含规划 10,240 tokens；未用额度不借用、不补写、不重跑 |

每个 writer 先获得 512 tokens，剩余 `7168−512T` 按其 `point_cap / sum(point_cap)` 用最大余数法分配；余数相同时按主题顺序分配。所有 writer 上限之和严格等于 7,168。每个主题实际返回 1 至其配额的非空要点，不要求写满；超量拒绝，不截断。

规划后冻结不可变配置、全体 writer/overview messages、schema、预算和 hash。所有写作输入在第一个 writer 前一次预检。来源正文上限与完整请求容量分开：候选完整模型可见请求封套（system/user 内容、JSON schema 和固定元数据的确定序列化）上限 80,000 字符，每次发送前再核对。该封套是本候选显式配置，不修改现有 `_bounded` 或全局 60,000 默认，也不能冒充精确 token/window 检查。

首轮 profile 拟复用已使用过的 Pro/Responses 原生 json_schema、reasoning none；供应商仍可能因输入窗口、配置或容量拒绝，必须首错停止，不自动调整容量或模型。真实调用前需核对当时官方协议并冻结实际参数，不增加能力探针或未列明 strict 参数。

与 A 的 high 思考、普通文本、16,384 token 上限和自由点数相比，B 同时改变了职责、格式、推理配置与容量。不能将效果单独归因于主题编排。14 点只是首轮有界压缩候选；若因此遗漏，也判失败，不通过缩小验收范围或同阶段抬上限补救。

## 7. 概览与最终结果

概览读取完整原文、冻结的主题标题/责任范围，要求高层主题关系；不接收前序生成正文，不重新生成或筛选要点。这样概览输入也能在写作前完成预检，避免付完写作成本后才因“全文+生成正文”超限。

取舍是概览不能依据实际措辞自动避免正文重复，重复仍须独立审阅；同主题高层重合允许，重复具体规则和无新信息复述仍失败。现有 overview 单字段 schema/解析可以复用，消息构造需接受本候选的冻结导航信息。

全部 writer 按规划顺序串行成功后，将要点原字符串按序组合，overview 成功后才构造一次 `LLMSummaryResult`。程序不执行最终全局 merge、不去重改写正文、不把源块覆盖认证为语义 coverage。

## 8. 错误、隐私与会计

任何 HTTP、provider、截断、解码、schema、容量、配置或已保存证据漂移错误立即停止；不重规划、不格式修复、不语义重试、不隐藏 fallback。已经生成的主题只作为诊断证据保留，不能返回部分产品成功。

LCEL 构造和执行全程禁 LangSmith/旧 LangChain 追踪。HTTP 零自动重试；无 provider SDK。凭据仅请求头，白名单响应不保存 reasoning、headers 或 secret。

设计审阅之后才写实现计划。代码/离线验证/独立审查通过后，首个新 phase 拟上限 8 POST，只验证一个已见来源；它不是当前已建立的预算分配。届时冻结 purpose、parent count/hash、source、全部候选资产和有限参数，root 共享 caller 锁、串行、发前持久预占，首错封账。不能重开 phase13 或通过新组抹去现有 35 POST / 304,248 tokens，旧 67 另封账。

## 9. 验证与验收

实现计划覆盖以下有意义的离线行为，使用假 transport，无真实模型：

1. 分块精确拼接、中文/英文/超长行/边界、非法/重复/缺失 ID、孤立主题、排序、上下文倍数和容量溢出均在 writer 前拒绝。
2. 资源分配整数和总量、动态 schema、本地严格校验、全部 messages 的预建与冻结一致性。
3. 实际 LCEL 职责、严格串行、T+2 上限、零重试、无部分结果、任一阶段错误停止、禁追踪。
4. 组合顺序与原字符串保持；overview 不重新生成 points；默认 single/staged、原配置与公开长度保护相关局部回归。
5. 独立验收 runner 的 root/共享锁、预占先于 POST、父组绑定、hash 漂移、错误封账及离线回放；不修改 closed 工具来续行。

内容验收仍逐断言核对完整 source：long1–6 所有必要子句必须 full，包含 phase13 已恢复的关系/条件；另检查课程路线主题、时间一致性、具体实例主体、模态与无新增含义重复。这里的具体历史缺陷只进入验收材料，不写成生成模板里的样本答案或固定主题。

B 不能以路由/schema/机械测试通过宣称内容通过。已见来源通过后，才安排未见 Lecture2 与短中篇，各自独立有限 phase 和准则；不在本 phase 自动扩展。整个候选仍未证明公开长文可用。

## 10. 设计决定与审阅入口

选择独立 LCEL 主题执行；不继续相同 A 请求或 merge 提示付费重复，也不引入带自动重试/恢复的图引擎。主要取舍是更多有限调用、原文重复投递和较紧的总输出预算，换取程序落实主题责任。精度与跨主题重复仍需内容证据。

用户审阅本文后，再按 writing-plans 形成实现计划并选择执行方式；当前不写产品实现、不运行测试、不发新 POST。旧原件、默认、公开入口和发布过滤规则均保持现状。
